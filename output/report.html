TB Bug

The testbench scoreboard does not account for the 1-clock-cycle synchronous read latency specified in REQ-012. The scoreboard immediately compares the current read address against the current rdata in the same cycle, sampling the stale rdata from the previous operation rather than pipelining the check to the following cycle.

Recommended Engineering Fixes

HIGH PRIORITY
Modify the scoreboard or monitor to model the 1-cycle read latency. In the scoreboard, buffer or pipeline the expected read transaction (address and expected data) so that it is compared against rdata one clock cycle later when the RTL read data becomes valid.

Root Cause: The scoreboard immediately checked tr.rdata against memory[tr.addr] in the same cycle a read was issued, ignoring the 1-clock-cycle synchronous read latency required by REQ-012.
Expected Behavior: Per REQ-012, read data appears on rdata one clock cycle after a read operation (we=0) is initiated with addr. The scoreboard must check rdata against the expected memory content of the previous read operation.
Why This Fix Works: Adding state variables `read_pending` and `pending_addr` allows the scoreboard to defer the comparison of read data until the following clock transaction arrives. In the next transaction, before updating state or checking new transactions, the scoreboard compares `tr.rdata` against `memory[pending_addr]`.
